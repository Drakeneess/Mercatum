# Mercatum V1 — Contrato de incursión con botín

**Estado:** V1 de prueba local/privada, primera vertical slice jugable. El combate, las criaturas, la muerte permanente, el comercio y una autenticación pública siguen fuera de alcance.

## Flujo jugable

1. Una persona elige siete atributos y firma su ficha. El servidor crea una cuenta pseudónima y un personaje, y devuelve una **credencial aleatoria de alta entropía**.
2. El navegador conserva la credencial en `localStorage["mercatum.session.token"]`. El servidor guarda únicamente su hash SHA-256 en PostgreSQL. En visitas siguientes, la credencial recupera **el mismo personaje**, sus stats y su posición.
3. El personaje puede avanzar por hexágonos vecinos según el cooldown **DES**. El servidor registra posición y siguiente movimiento permitido en la base de datos.
4. Hay una **puerta de servicio** en `q=1,r=0`. Puede abrirse mediante una acción temporizada de **FUE** o **INT**. Abrirla es un cambio permanente y compartido. No es obligatorio pasar por esa puerta: el plano contiene otros recorridos.
5. Una navaja oxidada única comienza en `q=2,r=0` (en una base nueva). Se puede **examinar** y **recoger** desde un hexágono próximo. Las acciones tardan tiempo de servidor, son cancelables y se interrumpen al desplazarse.
6. Una acción de recoger solo puede completarse por **un explorador**. La base de datos valida la posición, el estado del objeto y la capacidad, con transacción y bloqueo. El objeto pasa de `ground` a `carried`.
7. Volviendo a la entrada `q=0,r=0`, el personaje puede realizar una **extracción temporizada**. En una transacción, su botín `carried` pasa a `stash` y su estado cambia a `outside`.
8. Desde fuera puede revisar el depósito y **reingresar** con el mismo personaje. Los objetos del depósito no se llevan al reingreso automáticamente.

## Reglas de sesión y desconexión (F-001)

- **Cerrar la pestaña NO extrae el botín.** El personaje y sus objetos transportados siguen vinculados a la identidad y a la última posición.
- Una interrupción de WebSocket no crea otro personaje. La siguiente admisión con su token restaura su registro. No se garantiza conservar el mismo ID efímero de socket.
- Una segunda conexión simultánea con la **misma credencial** es rechazada mientras la primera siga activa. Si la pestaña anterior tarda en abandonar la sala, el cliente reintenta la entrada.
- Un movimiento rechazado no elimina ni reinicia el cooldown. El tiempo de movimiento se registra en PostgreSQL, por lo que reiniciar el backend tampoco acelera al personaje.
- Acciones incompletas **no progresan durante una desconexión o reinicio**. No se pagan ni completan parcialmente; las acciones deben solicitarse de nuevo.
- Actualmente **no hay muerte ni daño**, por lo que desconectarse estando dentro no produce castigo adicional. La regla de exposición a amenazas se diseñará en V2, antes de implementar permadeath.
- La navaja aparece **una sola vez por base de datos**; no se repone en cada reinicio. El servidor no regala copias nuevas cuando se agota el botín.

## Garantías del servidor

- El servidor autoriza decisiones de movimiento, puertas y objetos; el cliente no puede elegir coordenadas remotas ni inventar inventario.
- La tabla `market_objects` contiene una instancia única por ID. Los cambios de dueño, posición y estado se realizan por SQL parametrizado en transacciones. El campo `event_log` registra los hechos durables.
- El personaje solo puede transportar hasta `4 + 2 × Fuerza` unidades de peso (regla provisional); Resistencia y fatiga todavía no están implementadas.
- **FUE** e **INT** afectan la duración de apertura; aún no existen efectos de ruido ni desgaste de herramienta.
- El mapa tiene estructura tipada `SECTOR_01`; la puerta y los objetos tienen estado persistido.
- El estado compartido expone jugadores y si la puerta está abierta. El inventario, token y depósito solo se envían directamente a su propietario. Los objetos de suelo son públicos en V1; el filtrado sensible llegará antes de criaturas ocultas.

## Cómo ejecutar en Windows / PowerShell

Requiere **Node.js 22+, pnpm 10, Docker Desktop con Compose** o una instalación accesible de PostgreSQL 16+.

```powershell
cd D:\Mercatum\Mercatum
git status
git pull --ff-only origin main
pnpm install
docker compose up -d db
docker compose ps
pnpm dev
```

Interfaz en **http://localhost:3500**, servidor Colyseus en **http://localhost:3001**. El servidor instala las migraciones pendientes de PostgreSQL al arrancar y comprueba su conexión. La base de desarrollo se expone solamente en `127.0.0.1:5432`, con las credenciales locales de ejemplo definidas en `compose.yaml`.

Si usas PostgreSQL externo, no necesitas Docker; define tu propia variable `DATABASE_URL` en `apps/server/.env` o en el proceso de servidor. **Nunca utilices las credenciales de ejemplo en un entorno expuesto a Internet.**

```powershell
pnpm build
pnpm typecheck
pnpm test
pnpm --filter @mercatum/server smoke
pnpm --filter @mercatum/server smoke:v1
```

La prueba `smoke:v1` usa un esquema PostgreSQL temporal aislado; **no altera el inventario real de desarrollo**. Prueba: dos exploradores, una sola recogida aceptada, extracción atómica, reinicio de Colyseus, restauración del personaje y objeto conservado.

**No ejecutes `docker compose down -v` si deseas conservar los personajes:** la opción `-v` borra el volumen de PostgreSQL. `docker compose down` sin `-v` lo conserva.

## Limitaciones y pendientes

**No es un sistema de cuentas de producción.** Perder los datos del navegador implica perder el token y, por ahora, no hay recuperación de identidad. Un script malicioso ejecutado en el origen puede acceder a credenciales en `localStorage`; antes de una alfa pública hay que incorporar autenticación robusta, control de orígenes, protección contra abuso, rotación/revocación de credenciales y copias de seguridad.

Esta V1 demuestra un **ciclo de extracción**; no cierra todo el alcance ideal de los tickets. Siguen pendientes: equipar y transferir inventario entre jugadores, herramientas y efectos de ruido, balance de carga/fatiga, revisión visual manual en varios dispositivos, parametrización de más mapas/objetos, y controles operativos de despliegue. El comercio seguro y permadeath son hitos posteriores.

## Archivos principales

- `packages/shared/src/sectors.ts`, `world.ts`, `schema.ts`, `protocol.ts`: mapa, estado y contratos.
- `apps/server/src/storage/`: PostgreSQL, migraciones, identidad, objetos y estado de puerta.
- `apps/server/src/domain/actionPlan.ts`, `movement.ts`: validación y reglas.
- `apps/server/src/MercatumRoom.ts`: canal multijugador, temporización y commits del servidor.
- `apps/web/src/components/MarketActions.tsx`: interfaz de objetos, puertas y salida.
- `apps/web/src/hooks/useMercatumRoom.ts`: admisión, reconexión y mensajes de juego.
